## 已确认需求

- 在现有「按日期」「按网站」旁新增「按频次」，作为第三个平级入口。
- 默认浏览范围由最近三天调整为近一个星期，默认入口文案使用「近一个星期」。时间范围必须实际覆盖一周，不能只改显示文案。
- 用户可以选择时间范围；三个视图使用同一份当前时间配置，切换视图时保留该配置。
- 用户可以配置默认浏览时间。首次使用的默认值为近一个星期。
- 使用 ImageGen 出四版 UI，再对稿确定实现方向。

## 本轮设计方案

各版共用当前黑白圆角界面、三入口切换、时间范围和选择删除操作；差异集中在时间配置入口。全部使用虚构示例记录。

| 方案 | 时间配置方式 | 对稿重点 |
| --- | --- | --- |
| A：顶部下拉 | 结果标题旁直接展示「近一个星期」，下拉切换范围，提供设为默认的入口 | 当前范围是否一眼可见，是否延续现有布局 |
| B：筛选浮层 | 保留现有筛选按钮，浮层内选择时间及设为默认 | 是否减少工具栏占用，入口是否容易发现 |
| C：左侧时间栏 | 结果区内常驻时间选项及设为默认入口 | 切换效率与列表宽度的取舍，紧凑窗口如何收纳 |
| D：默认时间设置 | 当前范围快捷切换，默认浏览时间通过独立设置弹窗保存 | 是否清楚区分临时查看范围和下次打开的默认范围 |

以上是设计候选方案，默认时间保存入口、范围选项和布局以对稿结果为准。

## 建议在对稿时定稿的行为

- 「近一个星期」沿用现有日期筛选的本地自然日口径，包含今天及前六天；不另行改为滚动 168 小时。
- 本次时间范围可临时调整；只有明确选择「设为默认时间」或保存默认设置，才改变下次打开的范围。默认配置保存在本机。
- 复用已有今天、近三天、近一周、近一月、自定义日期能力，避免重复的一周选项。自定义日期是否可保存为默认，需要区分固定日期与滚动范围后再定稿。
- 频次视图第一版建议按网页展示，从高到低排列所选时间内的访问次数；次数相同时按最后访问时间排列。此处为待确认的排序方案，非既有行为。
- 现有带关键词搜索在未明确选择日期时使用全部时间。此次默认浏览调整先覆盖打开页面和空关键词浏览；是否同时调整关键词搜索默认范围，在对稿时明确，不顺带改变现有搜索语义。

## 实现前需要核实

- 当前 `extension/app.mjs` 的列表直接显示 `item.visitCount`。现有消费路径不能证明它是所选日期范围内的次数，不应直接将其标为「近一周访问次数」。
- 核实浏览器访问明细是否足以统计所选时间内的次数，以及历史保留、读取成本和加载状态。若只能提供累计次数，必须重新确认产品口径及标签，不用累计值冒充期间次数。
- 核实按期间访问筛选与目前按 URL 最后访问时间筛选的差异。例如：网页在选定范围内访问过、之后又访问过，期间频次视图是否应仍包含该网页。三个入口的范围含义需清楚说明。
- 检查完整页、弹窗、嵌入式窗口，以及中英文和明暗主题。四版桌面概念稿不能代替这些入口的实现验收。

## 未来规划：链接追踪参数净化与自定义规则

记录日期：2026 年 10 月 17 日。状态：已纳入未来需求池，待排期；不纳入上述下周交付承诺。本次只记录规划，不调整扩展功能、权限或商店配置。

目标：按用户配置移除链接中的广告追踪参数，保留页面正常访问所需的业务参数。区分插件内链接净化、已有历史记录处理与未来访问的请求净化，不将三者视为同一能力。

### 建议分阶段范围

- 优先评估插件内的净化预览、复制与打开。展示原链接和净化结果，原始浏览记录保留；此阶段可使用现有权限。
- 支持用户按网站定义待移除的参数名、例外和启停规则，配置保存在本机。具体预设参数及匹配范围在实现前确定，不直接截掉整个查询字符串。
- 后续评估可选的自动净化：用户主动启用并授予对应网站权限后，通过请求规则在未来请求发出前移除参数。建议默认关闭、按网站授权；是否提供所有网站模式另行确定。
- 已有历史记录的替换单独评估，不默认实施。Chrome 没有直接更新历史 URL 的接口，只能删除旧 URL、添加新 URL；不能承诺无损编辑。

### 已知能力与权限边界

- 现有 `history` 权限支持历史的查询、添加和删除，无需新增权限即可执行“删除旧 URL＋添加净化 URL”。但删除会移除该 URL 的全部访问记录，新增使用当前时间，无法保留原访问时间、次数及来源关系。事后清理也不能撤回网站已收到的参数。[History API](https://developer.chrome.com/docs/extensions/reference/api/history)
- 自动净化可使用 `declarativeNetRequest` 的 `redirect.transform.queryTransform.removeParams` 与动态规则。建议采用 `declarativeNetRequestWithHostAccess` 并按需申请 `optional_host_permissions`；现有 `activeTab` 不能覆盖所有网站首次访问时的自动处理。请求净化不等于原始 URL 一定不会进入 Chrome 历史，需独立实测。[请求规则](https://developer.chrome.com/docs/extensions/reference/api/declarativeNetRequest)、[重定向权限](https://developer.chrome.com/docs/extensions/develop/migrate/blocking-web-requests#redirect-multiple-urls)、[可选权限](https://developer.chrome.com/docs/extensions/reference/api/permissions)
- 若进入实现和上架，按最终功能同步更新商店描述、单一用途、权限理由和隐私说明。仅在本机处理也需准确披露；新增必需权限对老用户升级授权的影响需验证。[商店申报](https://developer.chrome.com/docs/webstore/cws-dashboard-privacy)、[权限更新](https://developer.chrome.com/docs/extensions/develop/concepts/permission-warnings)

### 实现前验收重点

- 使用虚构 URL 验证指定参数移除、业务参数保留、网站例外及规则停用；覆盖登录回跳、签名链接等不可随意删参的情况。
- 分别验证请求实际携带的 URL、地址栏和 Chrome 历史结果，不以其中一项代替其他结论。
- 若后续决定提供历史替换，先明确全部访问删除、时间及统计变化、净化 URL 已存在和部分失败时的行为，并在执行前展示影响。
- 自动模式验证按网站授权、拒绝与撤销权限、重开浏览器后的规则状态及关闭功能后的停用行为。
